# プロダクト開発 — PMプレイブック v1.0

## 思考原則
プロダクトは「顧客の問題を解決する機械」。最高のプロダクトは説明書なしで使える。ビルドトラップ（機能を作ることが目的化）を避け、常にアウトカムで考える。

## 必須フレームワーク

### 1. Jobs-to-be-Done（プロダクト開発版）
顧客は「問題」を解決するためにプロダクトを「雇う」。
- Functional Job：何を完遂したいか
- Emotional Job：どう感じたいか
- Social Job：どう見られたいか
→ Job Storyで設計：「[状況]のとき、[動機]を持つユーザーが、[期待するアウトカム]を達成できる」

### 2. Dual-Track Agile
```
Discovery Track：常に2〜3週先の問題を解明
    ↓
Delivery Track：検証済みのアイデアを実装
```
Discoveryなき実装 = ビルドトラップ。毎週20%の時間はDiscoveryに使う。

### 3. RICE スコアリング
優先順位 = (Reach × Impact × Confidence) ÷ Effort
| 要素 | 評価基準 |
|------|---------|
| Reach | 月間影響ユーザー数 |
| Impact | 0.25〜3倍（massive/high/medium/low） |
| Confidence | 0〜100%（証拠の強さ） |
| Effort | 人月 |

### 4. North Star Metric + Input Metrics
```
North Star：月間アクティブ利用時間
Input Metrics（←これを動かす）：
├── 新規登録数
├── オンボーディング完了率
├── 核心機能利用率
└── リテンション率D7
```

### 5. ユーザーストーリーマッピング
```
活動（Activity）→ ステップ（Step）→ ストーリー（Story）
     ↑
Backbone：最小限のユーザージャーニー
Walking Skeleton：MVP（初リリース範囲）
```

### 6. Shape Up手法（Basecamp式）
- 6週間サイクル：詳細な仕様書でなく「Shape（形）」された問題を渡す
- Cool-down 2週間：次のサイクルの準備・修正
- 「Appetite」（使えるリソース）で解の範囲を決める

## プロダクト開発プロセス

### Discovery（問題発見）
1. ユーザーインタビュー（週2件以上）
2. 行動データ分析（どこで詰まっているか）
3. Support ticket分析（繰り返し問い合わせ）
4. 競合ベンチマーク（他社の解法を学ぶ）

### 優先順位決定
1. 全アイデアをバックログ化
2. RICE採点
3. 戦略目標との整合性確認
4. 四半期ロードマップ確定

### 仕様策定
1. Problem Statement（解くべき問題の定義）
2. Success Criteria（成功をどう測るか）
3. Non-Goals（やらないこと）
4. User Stories（誰が何をなぜするか）
5. 受け入れ基準（AC）

## アウトプット品質基準

**優れたPRD（製品要件定義書）の条件:**
- 「Why」（なぜ作るか）が「What」より詳しく書かれている
- 成功指標（メトリクス）が定義されている
- 対象ユーザーセグメントが明確
- Non-Goals（範囲外）が明記されている
- エンジニアが迷わず実装できる受け入れ基準

**PRDの構成:**
```
【問題定義】誰のどんな問題か（JTBD形式）
【仮説】この解決策が機能すると考える根拠
【成功指標】Primary/Secondaryメトリクス
【スコープ】In / Out-of-scope
【ユーザーストーリー】主要シナリオ
【受け入れ基準】各機能の完了定義
【リスク・依存関係】技術的・ビジネス的リスク
```

## よくあるプロダクトの失敗
- HiPPO（Highest Paid Person's Opinion）で意思決定
- 機能過多：85%のユーザーが使わない機能が70%存在する
- 完璧主義：80点で早くリリースして学ぶ方が価値高い
- カスタマイズ地獄：全顧客の要望を聞くとプロダクトが崩壊
